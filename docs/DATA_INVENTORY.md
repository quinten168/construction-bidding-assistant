# Data Inventory: every field, every store, every writer

Issue #12. Read-only inventory taken 2026-07-22 against `main` at `8cf82fd`. Nothing was extracted,
no API was called, no store was written. The database was opened with `mode=ro` URIs only, and
verified real before use: `pipelines/plan_reader/csi_v2.db` is a symlink to the iCloud module copy,
160 MB (167,538,688 bytes), and `select count(*) from plans` returns 117.

## The gating question, answered first

**No, the live extract and the `04_tools` extract do not agree on the fields they both produce.**
Eight plans exist in both the per-plan JSON store (the live extraction pipeline's output) and
`csi_v2.db` (the `04_tools` batch output). Diffing the stored values, with no re-extraction:
quantities disagree on 4 of 8 plans, including one total miss where the live extract read 56,097
hot mix tons, 8,659 CY grading, and 185,188 SY milling and the batch parser found nothing at all
(`schedule_status = no_schedule_found`, zero `materials` rows). One plan has a bucket swap (40 tons
called `base_tons` by the live extract and `shoulder_tons` by the batch), one has a
`box_culvert` contradiction (live false, batch 1), and one differs by 6300 vs 6296 on hot mix
(LLM-read total vs deterministic bid-schedule sum). Gotcha counts differ on 7 of 8 plans, and page
citations for the same gotcha code disagree almost everywhere. The two paths also use different
join keys (PDF stem vs corpus plan_id), different work-type vocabularies, and each holds whole
field groups the other lacks. Details in the Disagreements section.

Also: the "three stores, four writers" framing in the work order undercounts. This inventory found
**10 stores and 13 writers** (evidence below).

## Disagreements

Recorded, not resolved. Ranked most consequential first. Empirical rows come from diffing the 8
plans present in both S4 (per-plan JSON) and S1 (`csi_v2.db`), plus the 1 plan present in S2 (the
payload cache), all from data already on disk.

**D1. The two paths do not share a join key.** The batch path keys everything on the corpus
plan_id (`2025_DOUGLAS-CO-MN_SAP-021-600-023_NOBID`). The live path keys the payload cache, the
Chroma chunks it ingests, and `conversations.active_plan_id` on the PDF stem (`9804001`), because
`report.py:80` defaults `plan_id = pdf_path.stem` and `report.py:106` passes only that. Nothing
maps one to the other except the manifest's source_file column. Every cross-store join between
live data and batch data is broken until this is reconciled.

**D2. Quantities: the batch parser can miss entire bid schedules the live extract reads.**
`2023_WATONWAN-CO-MN_SP-8303-48_LOST`: S4 has hot_mix_tons 56097, grading_quantity 8659,
milling_sy 185188. S1 has all quantity buckets NULL, `schedule_status = no_schedule_found`,
`bid_item_count = 0`, zero materials rows, and consequently `archetype = Unknown/NoQty` instead of
a real work type. This is the largest value-level divergence found, and it silently propagates
into classification.

**D3. Quantities: where both paths produce a number, the numbers differ.** The overlap plan
`2025_DOUGLAS...`: live 6300 (LLM whole-document read, cited to page 5) vs batch 6296.0
(deterministic sum of the parsed bid schedule line `TYPE SP 12.5 WEARING COURSE MIXTURE (3,C)`).
Two different derivations of the same concept. Related: gotcha page citations disagree on 8 of
the 9 codes both paths found on this plan (for example traffic_control p224 live vs p241 batch,
prevailing_wage p214/p133 live vs p213 batch); only liquidated_damages agrees at p29. The two
extractors appear to count pages on different bases and neither records which base it used.

**D4. Quantities: bucket assignment and boolean flags contradict.**
`2023_OTTER-TAIL-CO-MN_CP-4069-304_LOST`: the same 40 tons is `base_tons` in S4 and
`shoulder_tons` in S1. `2025_WATONWAN-CO-MN_WATLINE-TRAIL_NOBID`: `box_culvert` is false in S4 and
1 in S1. Both are direct contradictions on fields with identical names.

**D5. The live extractor disagrees with itself across runs.** The same PDF (9804001) was extracted
2026-06-11 (S4 record) and later via the app (S2 payload): county None vs Douglas,
construction_end 2025-10-10 vs 2025-10-24, traffic_level None vs SPWEB330C, prevailing_wage
gotcha cited p133 vs p214, material_source p200 vs p190. Neither store records the prompt or
model version that produced it (S4 has run_date only; S2 has nothing), so run-to-run drift is
invisible.

**D6. Three work-type vocabularies coexist.** The S4 records store `project_type` values from an
older taxonomy (Standard Paving, Complex/Messy, Earthwork Heavy). S1 and the S2 payload use the
5-archetype vocabulary (HMA Overlay/Resurface, Mill & Overlay, Reconstruct/Rebuild,
Grading/Earthwork, Aggregate/Base/Gravel) plus Unknown/NoQty in S1. `plans.project_type_llm`,
designed to hold the LLM's guess for cross-checking, is empty on every row checked. Within S1
the derived value is duplicated in `plans.archetype` and `plan_metrics.work_type`.

**D7. Same concept, different field names across stores.** sp_number (S2/S4/S5/S6) vs
dot_project_id (S1 plans). location (S2 identity) vs project_location (S4/S5). code (S2/S4) vs
flag_type (S1 gotchas/S5 flags.csv). quantities carry schema names in S4 but display labels (MIX,
BASE, t/CY/SY) in S2. Anyone consolidating has to carry a rename map.

**D8. Gotcha sets differ materially, not just cosmetically.** On the overlap plan: live 10
gotchas, batch 15. Batch-only: coordination, tight_schedule, environmental_species,
structure_work, water_permit_dewatering, density_lot_failure. Live-only: phasing_staging, which
directly contradicts the batch's `plan_metrics.has_phasing = 0` for the same plan. Across the 8
dual-store plans, counts differ on 7 (for example 10 vs 20 on 2023_WATONWAN, 8 vs 6 on
2023_WALSH). The batch side also carries decision_class, rationale, and evidence_status fields
the live side has no concept of.

**D9. Field-group coverage is disjoint.** Live-only fields with no S1 home: project_location,
traffic_level, bid_deadline, substantial_completion, final_completion, construction_start,
construction_end, phasing_requirements, special_requirements, per-field confidence and page
provenance. Batch-only fields with no live equivalent: outcome, contract_id, materials line
items, sections, all size/messiness columns, schedule_status and friends, decision_class,
duration as contract_duration_days rather than dates. Consolidating onto csi_v2.db means adding
homes for the live-only group.

**D10. Coverage gaps and dead structures inside S1 itself.** 17 of 117 plans have no plan_metrics
row. field_registry is created by 00_init_db.py and never populated (0 rows). doc_type holds
`combined`, a value the column comment does not admit. section_intelligence.low_sample_flag is
typed REAL but stores text, which already forced its exclusion from the Supabase publish. On the
overlap plan the batch parsed `AGGREGATE BASE (CV), CLASS 5 (P), 1922 CU YD` into materials but
left `plan_metrics.base_tons` NULL because the row's csi_bucket was never mapped, so a real base
quantity exists in one table of S1 and is absent from the rollup in another.

**D11. Type mismatches on shared fields.** Booleans are JSON true/false in S2/S4 and INTEGER 0/1
in S1 (prevailing_wages, box_culvert). Dates are ISO strings or free text in the live path,
INTEGER day counts in the batch path. Units are TON/SY/CY strings in materials, t/CY/SY labels in
the S2 payload, and implicit in the plan_metrics column names.

## Empirical basis and its limits
