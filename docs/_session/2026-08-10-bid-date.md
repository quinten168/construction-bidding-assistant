## 2. DIAGNOSIS — it is retrieval, not the boilerplate filter

**The chunk survives ingestion intact. Retrieval never surfaces it.**

Three independent methods, all named:

**Method A — raw metadata `get` scan of the Chroma store (no similarity involved).**
`collection.get(where={"$and":[{"doc_id":"2025_MURRAY-CO-MN_CSAH-2_NOBID"},{"page":9}]})`
returns **2 chunks**, `2025_MURRAY-CO-MN_CSAH-2_NOBID:p9:c0` and `:c1`. Chunk `c0` is 2,262 chars
and contains the deadline sentence **in full**, including "until **Thursday, August 7, 2025,** at
**11:00am** local time". Section `contract_front`, disposition `DOWN_WEIGHT` — down-weighted, not
dropped. The plan has 521 chunks across 396 distinct pages of 466.

**Method B — the production similarity query, at four values of k.**
Ran `retriever.retrieve()` with the exact query string `s4_extract_rag.SCALAR_QUERIES` uses for
`bid_deadline`, scoped to the same `doc_id`:

| k | pages returned | contains the bid date |
|---|---|---|
| 5 (**what s4 actually uses**) | 18, 22, 155, 56, 134 | **no** |
| 10 | + 157, 29, 13, 56, 23 | no |
| 20 | + 7, 22, 34, 131, 137, 24, 151, 45, 89, 72 | no |
| 40 | + … 9 … | yes, at ~rank 33 |

The top-5 for k=5, with cosine distances: p.18 `agreement` 0.327 (bid security forfeiture),
p.22 `bid_schedule` 0.383 (modifying a bid before opening), p.155 `contract_front` 0.386 (Notice to
Proceed), p.56 `agreement` 0.391 (liquidated damages milestones), p.134 `agreement` 0.408 (final
payment). Every one of them is a plausible neighbour of the query. **The page that actually
answers it ranks ~33rd.**

**Method C — the source PDF's own text layer, read directly with PyMuPDF**, independent of both
Chroma and the converter: page 9 of 466 contains the string. This is what rules out "the converter
lost it" as an alternative explanation for a Chroma miss.

### Why the query misses

`SCALAR_QUERIES` asks one query to serve **three** fields at once —
`bid_deadline`, `substantial_completion`, `final_completion` — so the query text is:

> "bid opening date bids due proposal deadline letting date substantial completion final completion
> contract time working days calendar days notice to proceed completion deadline liquidated damages
> complete the work by"

Two thirds of that string is about *completion*, and a 466-page proposal contains dozens of pages
of completion/contract-time/liquidated-damages boilerplate. They crowd out the one advertisement
page. This is a retrieval-dilution problem, not a filter problem.

**The boilerplate filter is exonerated on this plan.** The Advertisement for Bids page is tagged
`contract_front` → `DOWN_WEIGHT`, which is *kept and de-prioritised*, never `DROP`. It is in the
store.

## 3. What was built

**Not fixed by tuning the retrieval query.** A better query would still be a similarity gamble on
one page in 466, still cost a Claude call, and still fail silently. The bid deadline is a
deterministic string on a page that announces itself. It is now read deterministically.

| file | what it is |
|---|---|
| `pipelines/plan_reader/04_tools/bid_date/bid_date.py` | the parser — layers 1, 2, 3 |
| `pipelines/plan_reader/04_tools/bid_date/test_bid_date.py` | 50 tests, incl. 2 corpus coverage floors |
| `pipelines/plan_reader/04_tools/bid_date/measure_bid_date.py` | the hit-rate harness |
| `apps/api/backend/bid_date_bridge.py` | live-path bridge, same pattern as `midpoint_bridge.py` |
| `apps/api/backend/report.py` | new 7th `process_pdf` stage + layer 3 in `apply_verification` |
| `apps/api/backend/config.py` | `BID_DATE_DIR` |
| `docs/_session/2026-08-10-bid-date-layer1.csv` / `-layer2.csv` | per-file measurement output |

**Naming deviation, flagged deliberately.** The working rule says every file gets a `YYYY-MM-DD`
prefix. `bid_date.py` and `bid_date_bridge.py` are **imported at runtime**, and a leading date is
not a valid Python identifier — CLAUDE.md invariant 2 turns on these modules being path-imported
by name. They follow the existing precedent for runtime tool modules
(`04_tools/road_midpoint/road_midpoint.py`, `04_tools/reverse_geocode/reverse_geocode.py`, neither
dated). Every **document and measurement artifact** I produced is dated. Say the word and I will
rename, but it will need an `importlib` shim.

### Layer 1 — the standalone advertisement PDF

Finds `<n> AD.pdf`, `* AD FOR BIDS.pdf`, `*Advert*.pdf` etc. next to the plan set, excluding
addenda (`a1.pdf`, `*addendum*`), smallest first so a two-page ad beats a 250-page document that
merely has "ad" in its name.

### Layer 2 — the Advertisement for Bids page inside the plan set

Runs the **same scanner** over the already-converted markdown pages `process_pdf` is holding
anyway. **No extra PDF read, no embedding, no Claude call.** This is the layer that carries the
load (see §5).

### Layer 3 — human entry

`bid_date_bridge.parse_human_entry()`. When the verify popup sends `bid_deadline`,
`apply_verification` re-derives `bid_date` / `bid_time` from it — otherwise the human fixes the
display string and CI still sees a null `bid_date` and still lands in the wrong season.

Layer 3 deliberately applies **no** anchor scoring: someone typing into a box already labelled
"Bid deadline" has done the disambiguation. Accepted shapes, all tested:
`August 7, 2025` · `2025-08-07` · `2025-08-07 11:00` · `2025-08-07T11:00 CT` (datetime-local) ·
`8/7/2025 11:00 AM CT` · `Thursday, August 7, 2025 at 11:00am local time`.

**Wenyu: the field exists and is populated. Nothing in `apps/web/` was touched.** The payload's
`identity` now carries `bid_date`, `bid_time`, `bid_timezone`, `bid_deadline_layer`,
`bid_deadline_source`, `bid_deadline_page`, `bid_deadline_evidence`. `identity.bid_deadline` keeps
its existing free-text shape so `report-card.tsx`, `verify-extraction.tsx` and
`bid_projects_record.parse_bid_date` all keep working unchanged. Sending an edit for
`bid_deadline` through the existing finalize endpoint is all layer 3 needs to do; it also sets
`identity.bid_deadline_parsed` so an unparseable entry is visible rather than silent.

### The standing rule, honoured

`BidDateResult.status` is `found` / `not_found` / `error`, and they are three different things.
`8381821 AD.pdf` (Renville Co ND) is a subset TrueType font with no cmap — its text extracts as
mojibake. That is reported as **`error: broken font encoding`**, not as "this advertisement has no
bid date". Likewise a missing file, an unopenable file, and an image-only scan are all errors.

  status=not_found       : 2
  status=error           : 1

Every failure characterised:

| file | outcome | why |
|---|---|---|
| `8381821 AD.pdf` (Renville ND) | **error** | broken font encoding, mojibake. Needs OCR or a cmap fix. The only true parser-unreachable file. |
| `Ad for Rd Maintenance.pdf` (Pope MN) | not_found | **correct.** Scanned note: "According to Terri Mitchell, there are no bid docs for this project." |
| `AD.pdf` (Lincoln SD) | not_found | **correct.** "Per Delapre Twp there is no bid form or bidding documents for this project." |
| `8370470 AD.pdf` (McLean ND) | found, disagrees | parsed `2022-10-13 14:00`; folder says `02.23.23`. **Corpus error, not parser error** — a stale October-2022 advertisement is sitting in a February-2023 folder. The parser read it correctly. |
| `007-626-019 AD FOR BIDS.pdf` (in the Pope MN folder) | found, disagrees | parsed `2023-04-26`; folder says `04.27.23`. **A Blue Earth County advertisement filed in a Pope County folder.** The same folder also holds the correct `Advert SAP 061-615-008.pdf`, and the orchestrator's smallest-first ordering picks that one — `extract(project_dir=…)` on that folder returns the right answer, `2023-04-27 10:00`. |

**So: 19/19 documents that actually state a bid deadline were parsed, 100% of them with a clock
time. The 3 non-hits are 2 documents with no bid date and 1 unreadable file. The 2 disagreements
are both wrong-file-in-folder, and one of them the layering already survives.**

### Layer 2 — 16/17 converted plans

Run over `pipelines/plan_reader/00_input/_md_cache/` (17 real plans, fully local, no Box, no
re-conversion). Correct date **and** time on 16, including all four state-DOT proposal-cover
formats and the Fulda page-9 case that started this.

The one `not_found` is `8395536` (Divide Co ND) — the plan set genuinely does not state a bid
deadline; it states only the **deadline for written questions** ("Written requests must be received
by 1:00 p.m., Friday, February 24th, 2023"), a week before the real bid date. An earlier revision
of the parser returned that as the bid date. It is now vetoed, and the correct value comes from
layer 1: the standalone `8395536 AD.pdf` gives `2023-03-03 15:00`, which matches the folder. **This
single plan is the clearest argument for the layering.**

### What the measurement changed in the parser

Five defects the numbers caught that a single-file test never would have:

1. `N.D.A.C. 4-12-10` parsed as 12 Apr **2010** → a 2010 bid deadline on a 2023 plan. Numeric dates
   now require a 4-digit year; a 2-digit year is only believed directly after an explicit label.
2. `plans approved 7/31/2025` returned as a bid date. Plan-approval / certification is now a veto.
3. The **bidder-question deadline** winning over the bid deadline (the 8395536 case above).
4. `11 : 00 AM CT` — the converter spaces the colon out of table cells; the time regex missed it
   and the field came back date-only.
5. **Negatives were scored over too wide a window.** "THE APPROVED DEPARTMENT OF TRANSPORTATION
   STANDARD SPECIFICATIONS", two lines below `Letting Date:` on **every MnDOT/SDDOT proposal
   cover**, vetoed the bid date on the whole state form. Negatives now score in a ±110-char window
   (a disqualifier governs the date it is attached to); positives still score in ±320. This one
   change took layer 2 from 14/17 to 17/17 before defect 3 was fixed.

### Tests

50, all passing. The load-bearing ones are coverage, not units:

- **21 verbatim corpus phrasings** (MN/ND/SD, 2023 and 2025, seven different firms' boilerplate,
  plus both state-DOT proposal-cover forms) that must each still parse — including one aggregate
  assertion that goes red the moment the matcher covers fewer than all of them.
- **`test_corpus_layer1_hit_rate_does_not_regress`** — re-runs layer 1 over the real corpus and
  fails below 19/22. Skipped, never silently passed, when the corpus is absent.
- **`test_layer2_coverage_over_converted_plans_does_not_regress`** — re-runs layer 2 over

- Six tests that a failure and an empty answer do not share a return value.

`apps/api` suite: **49 passed, 2 failed**, and both failures are pre-existing — verified by

## 5. Corrections to the board

**a. "217 standalone advertisement PDFs" is wrong, and it changes the plan.**
Counted three ways on the local mirror: strict `* AD.pdf` → **8**; my broader advertisement matcher
(`AD`/`ADVERT` token, addenda excluded) → **22**; addenda `*a[0-9].pdf` → **327**. The board's 217
is advertisements and **addenda** counted together, and the addenda dominate it. The 8 strict ones
are all 2023-bid-year.

**Consequence, stated plainly: layer 1 covers ~22 project folders out of 95+ in the 2023 year
alone. It cannot be presented as the main path.** It is still worth having — it is cheap, it is
authoritative where it exists, and 8395536 proves it recovers a plan layer 2 cannot. But **layer 2
carries the load**, and layer 2 measures 16/17. My broader matcher is worth keeping over the strict
glob: it finds 14 advertisements the `* AD.pdf` glob misses (`AD FOR BIDS`, `Advert …`,
`Advertisement for Bids`, `Ad for Bid`).

**b. Daily Ads is a real asset but not this week's.** 174 digests. They are QuestCDN exports with a
rigidly structured field — `Closing Date: Thu, 01/15/2026 02:00 PM CST` — alongside `Quest Number`,
owner, county and state. Trivially parseable. Three things stop it being a shortcut today:

- **53 of the 174 have no text layer at all** (image-only, would need OCR).
- Across the 121 that do, only **111 distinct closing-date strings and 77 distinct Quest Numbers**
  — the digests repeat the same postings day over day, so the yield is far below one-per-digest.
- **The join key exists but does not join on this corpus.** `Quest Number` is exactly the numeric
  plan-set filename stem (the Walsh advertisement says "inputting Quest project # 8376434" and the
  files are `8376434.pdf` / `8376434 AD.pdf`). But of 202 numeric plan stems in the corpus, only
  **1** appears in a Daily Ads digest — Daily Ads covers Sep 2025 → Jun 2026 and the numeric-stem
  plan folders are the 2023 bid year.

  Recommendation: **do not build a layer 0 on Daily Ads before Wednesday.** Log it as the best
  available source of *forward-looking* bid dates for projects we have not been sent plans for —
  a regional bid calendar — which is a different feature from filling a field on a dropped plan.

**c. The folder name is a better bid-date source than either layer, and it is free.**
`02.16.23 WALSH CO ND - …` gave ground truth for 17 of the 22 layer-1 files, and it caught two
wrong-file-in-folder errors the documents themselves could not. It has no time component, so it
does not replace the parser, but for **backfilling the historical corpus** it is stronger than
parsing anything. It also confirms the identity decision already on the board.

**d. Retrieval dilution is not specific to `bid_deadline`.** The same `SCALAR_QUERIES` entry serves
`substantial_completion` and `final_completion`, both from the same k=5 pull. Those two fields have
the *same* diagnosis and no deterministic fallback. That is P0 #5's problem, and #5 should inherit
this finding rather than rediscover it.

## 6. Proposed `schema.py` text — for the main session to apply

`schema.py` was not touched. Current text (`01_pipeline/schema.py:115`):

```python
    _f("bid_deadline", "str", "rag",
       "Bid opening / bid submission deadline — the date (and time + time zone if given) bids are "
       "due. Usually on the advertisement or proposal cover. Return as written; null if not stated.",
       golden=None, evalkind=None, group="constraints", doc="either"),
```

**It should change.** Two reasons: it does not tell the model what to *avoid*, and three of the
four wrong answers the deterministic parser had to be taught to reject (pre-bid conference,
bidder-question deadline, plan-approval date) are exactly what an LLM handed five retrieved chunks
will grab. It also does not name the state-DOT `Letting Date` / `Bids Close` form, which is how
every MnDOT and SDDOT proposal cover states it.

Proposed replacement:

```python
    _f("bid_deadline", "str", "rag",
       "Bid opening / bid submission deadline — the date AND clock time (with time zone if given) "
       "that bids are due. Usually on the Advertisement for Bids page or the proposal cover, worded "
       "'bids will be received … until <time> on <date>'. MnDOT/SDDOT proposal covers state it as "
       "two labelled fields instead: 'Letting Date: August 20, 2025' with 'Bids Close: 9:30 a.m. "
       "CST' — combine them. Do NOT return: a pre-bid conference date, a deadline for bidder "
       "questions or substitution requests (usually a week earlier), a plan-approval or "
       "certification date, or a substantial/final completion date. Return as written; null if not "
       "stated.",
       golden=None, evalkind=None, group="constraints", doc="either"),
```

Non-breaking: same name, type, source, group and `doc`; description only, and the return contract
("as written", "null if not stated") is unchanged. `bid_projects_record.parse_bid_date` handles
every shape this can now produce.

**Note the layering, though:** as of this commit the deterministic stage overwrites
`record["bid_deadline"]` whenever it finds one, so the RAG value is the *fallback*, not the primary.
The description still matters for the plans where the deterministic read comes back `not_found`.
