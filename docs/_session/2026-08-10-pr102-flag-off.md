## 2. The flag

**Where:** `pipelines/plan_reader/01_pipeline/material_tons_merge.py`.
**Name:** `CONVERSION_ENABLED`. **Default: `False`.**

### 2.1 It is a code default, computed at import — there is no configuration to get wrong

Per `docs/_spec/2026-08-10-placed-material-conversion.md` §9.2, the flag is not a boolean anybody
sets. `CONVERSION_ENABLED = _compute_conversion_enabled()` runs once at import and ANDs three
independent gates, each of which evaluates `False` under inaction:

| gate | reads | why it is False today |
|---|---|---|
| **G1 blessed** | `FACTOR_TABLE[*]["blessed_by"]` and `["blessed_on"]` | Both empty strings on both rows. Nobody at CSI has signed the factors. Forgetting to obtain a signature leaves the flag off; there is no separate "remember to switch it off" step to forget. An empty table is also `False`, not vacuously true. |
| **G2 reproduces** | `03_evaluation/outputs/2026-08-10_conversion_acceptance.json` → `passed is True` | **The file does not exist.** A missing file, an unreadable file, or a file that does not literally say `"passed": true` are all `False`. Absence is never read as success. |
| **G3 operator opt-in** | env `PLAN_READER_MATERIAL_CONVERSION` | Unset ⇒ `False`, silently (the ordinary case). Set to anything other than the exact token `on` ⇒ `False` **plus a printed warning**, so a misconfigured operator finds out rather than quietly getting pre-#102 numbers. |

A fresh clone is therefore OFF with no action taken, and `git grep` for a config file to fix finds
nothing, because there is none. Turning it on requires three deliberate positive acts from three
different kinds of authority: CSI (a signature), a recorded test run, and an operator.

The factor constants are **not** blanked out — they are recorded in `FACTOR_TABLE` with a `basis`
field labelling each as an **ASSUMPTION** (`113 lb/SY-in ÷ 2000` and `3,100 lb/CY ÷ 2000`, MnDOT
reference conversion table, CSI-supplied 2026-08-10, not traced to a printed spec-book page). Per
the standing rule, an unconfirmed factor is used as a labelled data-validated assumption rather than
being a reason to block — the labelling lives in the table, and the *gating* is separate.

### 2.2 With the flag off, the behaviour is the pre-#102 behaviour

`merge_material_tons` skips `_sum_items` entirely and returns the native TON extraction only. Since
`report.py::_effective` falls back to `_val(record.get(src))` on a `None`, every downstream number —
`quantities`, the archetype rule input `qrow`, and the `scratch.bid_projects` row that reads
`payload["quantities"]` verbatim — is exactly what it was before #102. Proven in §4.

Two additions to the payload that did not exist pre-#102, both deliberate and neither a quantity:
`field_confidence["base_cy_items" / "shoulder_cy_items" / "mix_sy_depth_items"]` (#102's, kept — it
is evidence, not a derived value) and `identity.{base,shoulder,mix}_conversion_status` (new here,
§3). The spec anticipates exactly this: *"the demo path with the flag off is the demo path as it is
today, with one extra explanatory status string."*

### 2.3 The extraction still runs

The three items fields are still requested from the model with the flag off, and `max_tokens=6000`
stays. This costs tokens for a value nobody sees — and it is the right trade, because it is what
lets the system say **"a real tonnage exists on this plan and we withheld it"** instead of nothing.
It also means flipping the flag later is a one-line change with no prompt change and therefore no
new extraction-drift risk.

## 3. OFF is a state, not a silence

The brief's fourth requirement, and the repo's standing rule. `material_tons_merge.conversion_report(record)`
returns one entry per bucket carrying a `status` from a closed vocabulary plus the counts behind it:

| status | means |
|---|---|
| `disabled_withheld` | flag off, **and ≥1 item would have converted** — a real tonnage exists and is being withheld |
| `disabled_nothing_convertible` | flag off, items captured, none convertible anyway (e.g. SY with no stated depth) — turning the flag on would change nothing here |
| `disabled_not_applicable` | flag off, model asserted an empty list — genuinely nothing to convert. A real answer. |
| `disabled_unknown_input` | flag off, items field is `null` — extraction gave no answer, so we cannot even say whether anything was withheld |
| `all_converted` / `partly_converted` / `none_converted` / `not_applicable` / `unknown` | the flag-on equivalents |

Four situations that all produce `base_tons is None` are four distinguishable statuses — asserted by
`test_withheld_is_distinguishable_from_nothing_to_convert`, which fails if any two collapse.

**What the status deliberately does NOT carry: the withheld tonnage.** Handing a consumer the number
the flag exists to withhold is the exact failure the flag prevents. The counts say a number exists;
they do not leak it. `test_the_status_never_leaks_the_withheld_tonnage` pins that.

Surfaced at `identity.base_conversion_status` / `shoulder_conversion_status` /
`mix_conversion_status` in `report.py`. These are new key names and do **not** collide with either
branch's `*_unit_status` keys — they answer a different question (*what did this system do?* vs
*what did the schedule measure?*).

## 5. The follow-up commit — what step 2 must do. NOT implemented here.

### 5.1 Per-value provenance

A converted number must be distinguishable from a stated one **at the value**, not at the bucket.
Today `report.py:289-297` appends `{"label": "BASE", "value": 3851.75, "unit": "t"}` — byte-identical
in shape to a plan that printed 3,851.75 on its schedule. Required per converted value:

- the **input quantity and unit** as printed (`2,485 CY`);
- the **depth used**, and `null` where none was needed (F2/CY needs none — do not gate on depth);
- the **factor applied, carried as a literal, labelled as an assumption with its MnDOT basis** —
  `1.55 ton/CY (assumption: 3,100 lb/CY, MnDOT reference conversion table, CSI-supplied 2026-08-10,
  not traced to a spec-book page)`. A literal, not a pointer into `FACTOR_TABLE`, so a report
  printed today still explains itself after the table is edited;
- the **source page** for each contributing line.

**The specific defect to fix, found in validation §4.3 and re-confirmed here:**
`report.py`'s `field_confidence[label] = _conf(field)` reads the **native** cell. On 9786015 that
cell is absent, so `schema.cell(None, "", None)` → `{'confidence': '', 'page': None, 'reason': None}`.
**A fully-derived 3,851.75 t would render with blank confidence and no page citation**, while the
real evidence — `confidence: high, page: 27` — sits under `field_confidence["base_cy_items"]`, a key
**no quantity row points to**. Fixing provenance means fixing this link, not just adding fields:
the confidence/page shown against `BASE` must come from whichever cell actually sourced the value.

Shape is already specified in `docs/_spec/2026-08-10-placed-material-conversion.md` §6
(`<bucket>_converted_tons` / `_converted_lines` / `_conversion_status`, closed `reason` vocabulary,
`factor_value` as a literal). Use it; do not design a third one.

### 5.2 The two internal collapses

**(a) `merge_material_tons` returns `None` for both failure and empty.** A plan with no base at all
and a plan with a real base item measured in GAL both return `base_tons = None`. `_combine` returns
`None` when "both components are absent", and an all-unconvertible items list produces
`cy_total = None` via `_sum_items`. The `disabled_*` statuses added here cover the flag-off case
only — they do **not** fix this, which lives in the flag-on path. Fix: `_sum_items` must distinguish
"nothing to sum" from "items present, none summable", and that distinction must reach the caller.

**(b) The excluded quantity never reaches the payload.** `report.py:323` writes
`field_confidence[cy_field] = _conf(record.get(cy_field))`, and `_conf` (`report.py:104-112`) returns
**only** `{confidence, page, reason}` — it drops the value. So the raw items list, including any
quantity that was seen and excluded, exists nowhere in the payload; it survives only inside the
model's prose `reason` string. Live instance in the corpus: `823d011b34af0e82` reports
`mix_unit_status = 'sy_no_depth_present'` with 4 items and `hot_mix_tons = 4,892.9` — a **partial**
total, with the excluded quantity unrecoverable.

Also note, though not one of the two: `_aggregate_unit_status` computes `has_tons` and then never
uses it once `items` is truthy, so a genuine TON+CY bucket reports `cy_only` while its value is a
blend. There is no `tons_and_converted` state in `AGGREGATE_UNIT_STATUSES`. Fix this in the same
pass as §5.3, since it is a vocabulary hole.

### 5.3 The field reconciliation — precise token lists

Two branches emit overlapping keys with **partly-disjoint** vocabularies. A consumer of one reading
the other's payload hits a token it has no branch for and falls through to "Not captured" — a bucket
that was captured fine rendering as a failure.

| | `2026-08-10-mapping-honesty` (2a) | `fix/aggregate-mix-tons-conversion` (#102) |
|---|---|---|
| mix key | **`hot_mix_unit_status`** | **`mix_unit_status`** |
| base key | `base_unit_status` | `base_unit_status` |
| shoulder key | `shoulder_unit_status` | `shoulder_unit_status` |
| how emitted | computed, `f"{bucket.rsplit('_', 1)[0]}_unit_status"` over `schema.TONS_BUCKETS` | three literal keys in `report.py` |
| **vocabulary** | `tons_only` · `unconverted_only` · `tons_and_unconverted` · `not_present` · `unknown` · `inconsistent` | `tons_only` · `cy_only` · `sy_converted_only` · `mixed` · `sy_no_depth_present` · `not_present` · `unknown` · `inconsistent` |

- **Shared tokens (4):** `tons_only`, `not_present`, `unknown`, `inconsistent`.
- **Only 2a (2):** `unconverted_only`, `tons_and_unconverted`.
- **Only #102 (4):** `cy_only`, `sy_converted_only`, `mixed`, `sy_no_depth_present`.

Two distinct failure modes, and the second is the quieter one:

1. `hot_mix_unit_status → undefined` for a 2a consumer on a #102 payload — an absent key, at least
   detectable.
2. `base_unit_status = "cy_only"` — a **valid key with a valid-looking value that 2a's vocabulary
   does not contain**. Any `switch`/lookup falls through to its default and renders "Not captured"
   for a bucket that was captured perfectly.

**What step 2 must decide and encode:** one key set (recommend 2a's computed form — it cannot drift
from `TONS_BUCKETS`, so `hot_mix_unit_status` over `mix_unit_status`) and **one closed vocabulary
that retains a both-units state** (2a's `tons_and_unconverted`, which #102 has no equivalent for —
see §5.2's note). Then a test that asserts every emitted token is a member of that closed set, so a
future divergence fails loudly instead of rendering as "Not captured".

Confirmed here against the live app's own cache: `00_input/_report_payload_cache/a3171c2187e8af85.json`
currently carries `identity.base_unit_status = "unconverted_only"` and
`identity.mix_unit_status = null` — i.e. the main checkout is serving **2a's** vocabulary right now.
Merging #102 as-is would change that key's value space underneath a live consumer.

## 7. Expected conflicts on rebase

Three agents are working in the main checkout on `schema.py`, `apps/web/**`, `report.py` and
`s3_extract.py`. Concretely expected, in likely-difficulty order:

1. **`apps/api/backend/report.py`, the `identity` dict.** #102 inserts three keys immediately after
   `"milling_unit_status"`; this branch inserts three more right after those; 2a inserts its own
   computed `*_unit_status` keys in the same place. **Three-way conflict on adjacent lines, near
   certain.** Resolution is mechanical (keep all, dedupe by §5.3's decision) but must be done by
   hand — an auto-merge that keeps both key sets ships the vocabulary collision.
2. **`pipelines/plan_reader/01_pipeline/s3_extract.py::extract_fields`.** Both #102 and 2a replace
   the same `data = call_json(prompt) or {}` line. **Textual conflict, certain.** Prefer 2a's
   `EXTRACT_MAX_TOKENS` named constant plus `stop_reason` inspection over #102's inline `6000`.
3. **`pipelines/plan_reader/01_pipeline/schema.py`.** #102 inserts three field definitions into
   `SCALAR_FIELDS`; 2a inserts six. Different insertion points, so possibly a clean auto-merge —
   but the result is **9 new fields on one extraction call**, asking the model to enumerate the same
   bid item twice in two different shapes. That is a design decision, not a merge decision, and
   §5.3 is where it gets made.
4. **`CLAUDE.md` rough edge 12.** Rewritten here to state that the engine is dormant. If #102's
   version of that entry lands anywhere else it will conflict, and #102's wording is now *wrong* —
   it describes values being merged into the buckets, which with the flag off they are not.
