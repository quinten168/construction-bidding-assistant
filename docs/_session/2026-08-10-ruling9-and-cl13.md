## Fix 1 — CSI ruling #9 (FULL DEPTH RECLAMATION → `milling_sy`)

### What was wrong, measured rather than assumed

Stearns 9813645's bid schedule prints, on the same page the model receives:

```
|13|2215.504/00010|FULL DEPTH RECLAMATION   |S Y| 70167|
|15|2232.504      |MILL BITUMINOUS SURFACE (1.0")|S Y| 68167|
|16|2232.504/00040|MILL BITUMINOUS SURFACE (1.5")|S Y|    96|
|17|2232.504      |MILL BITUMINOUS SURFACE (4.0")|S Y|  2000|
```

Before the fix, `milling_sy` came back **70,263 on 9 runs of 10** and the model's own stated reason
said, nine times, *"Bid schedule items 15, 16, 17"* — item 13 was never mentioned. The clause naming
FDR was written as a parenthetical gloss inside the milling item list, and read as a note about the
milling items rather than as a second thing to add.

Two further facts the source document supplies, both load-bearing:

1. **The same 70,167 SY is restated later in the document under a different name** — the
   "Approximate Major Quantities" page says `Bituminous Pavement Reclamation 70,167 SY`, right
   beside `Mill Bituminous Surface 70,263 SY`. A description that names only "FULL DEPTH
   RECLAMATION" does not cover the way the document summarises it.
2. Every bid-schedule row on that page is wrapped in markdown strikethrough (`~~…~~`) by the PDF
   converter. This did not stop the model reading the milling rows, so it is not the cause — noted
   so nobody re-litigates it.

### The change

`milling_sy` is now stated as **one total made of two kinds of line**, with the reclamation kind as
a first-class addend rather than a gloss; the corpus's other names for it are listed
(`FDR`, `STABILIZED FULL DEPTH RECLAMATION`, `BITUMINOUS PAVEMENT RECLAMATION`, MnDOT item
`2215.504`); and the worked example uses **numbers that are not this plan's** (12,000 + 300 + 40,000
= 52,300), because using Stearns' own numbers would be teaching to the measurement.

### Five arms, because the first four were worse — the honest path

Every arm is N=10 on the same held-constant input. This is recorded in full because four of the five
prose variants introduced a *different* defect, and the shape of each failure is the finding.

| arm | arithmetic wording | Stearns `milling_sy` | Dunn OK | note |
|---|---|---|---|---|
| before | (FDR as a parenthetical) | 70,263×9, 140,430×1 | 10/10 | ruling does not fire |
| `after_fix1` | "sum of two kinds, add them together" | 208,430×6, 140,430×2 (8 OK) | 10/10 | **FDR now always found**, but double-counted |
| `after_fix1b` | + "never re-add a line inside a subtotal" | 140,430×4, 138,430×5 (9 OK) | — | double count fixed, 4-addend sum drops a line |
| `after_fix1c` | + "check you have one addend per line" | 140,430×1, 138,430×4, 208,430×1 (6 OK) | — | **4 parse failures** — the instruction made the model narrate |
| `after_fix1d` | "add in two steps: kind-(a) ONLY, then kind-(b)" | 140,430×9, 140,693×1 (10 OK) | — | best accuracy … |
| `after` | fix1d + the first (verbose) CL 13 prose | 140,430×10 | **3/10** | … but Dunn collapsed: 7 of 10 responses opened with a prose preamble instead of JSON |
| `after2` | declarative "disjoint sets, subtotal + subtotal" | 208,593/208,597 (8 OK) | 10/10 | double count returns |
| `after3` | hybrid | 4-way split (8 OK) | 5/10 | worst of both |
| **`after4` (shipped)** | **"add the LINE ITEMS themselves, each exactly once — do not build subtotals"** | **140,430×8, 208,430×1, 208,593×1 (10 OK)** | **10/10** | best balance |

Two generalisations worth keeping:

- **Procedural instructions ("do X, then Y, then report Z") buy accuracy and cost parseability.**
  The two arms with step-by-step wording produced the best numbers *and* the two worst parse-failure
  rates (7/10 on Dunn, 4/10 on Stearns), because the model wrote the procedure out before the JSON.
  Declarative constraints parse reliably and permit the double count. `after4` gets most of the
  accuracy by naming the *unit of addition* (a line item) rather than a procedure.
- **The residual errors are arithmetic, not identification.** After the fix the model finds the FDR
  line in 10 runs of 10, every time, on both plans. The 2 Stearns misses are ~208,4xx — the milling
  subtotal added twice — not a return to 70,263.

### Stated limitation (per the standing rule: a labelled 8/10 beats an unlabelled 10/10)

**FDR folding applies where it fires. Known gap: `milling_sy` on a plan carrying BOTH milling and
reclamation lines returns the correct combined total 8 times in 10; the other 2 double-count the
milling subtotal (~208,4xx on Stearns).** A plan carrying only one of the two kinds — which is every
other plan measured, including both ND plans — is unaffected: Dunn 408,216 and Job 24133 152 were
each unanimous at 10/10.

### Dunn regression check — held

`milling_sy = 408,216` (the FDR line on that plan) was **10/10 before and 10/10 after**, with
`milling_tons` still carrying the ND ton-measured milling (67,007 ×8, 66,007 ×2 — pre-existing
noise, unchanged in character from the before arm's 67,007 ×9 / 66,007 ×1) and
`milling_measured_unit = SY+TON` 10/10. `base_tons` 6,506 ×9 (one run at 7,326, which adds the 820 T
`TRAFFIC SERVICE AGGREGATE` — pre-existing ambiguity, present in the before arm's model reasoning
too, not introduced here). `grading_quantity` remains the known-noisy field it was before this
change (5 distinct values before, 5 after) and is untouched by it.

### The demo pin moved

`tools/2026-08-10_rewarm_demo_cache.py::DEMO_PLANS` no longer pins Stearns `MILL: 140430`.
**140,430 is still the correct number** (70,263 SY of milling + 70,167 SY of FDR) — it is unpinned
because it reproduces 8 times in 10, and an equality check on an 80%-reproducible value reports
FAILED on a correct run 20% of the time. What is pinned instead is the four Stearns fields that were
**unanimous across both N=10 arms**: `MIX 14,480 · BASE 270 · GRADE 200 · SHLDR 460`. The plan's
`why` note — now printed at re-warm time — tells the operator exactly what to compare MILL against
and what each deviation means (70,263 = the ruling stopped firing; ~208,4xx = the known arithmetic
slip; anything else = investigate).

## Fix 2 — the CL 13 vocabulary gap

`AGGREGATE SURFACE COURSE CL 13 | TON | 170` (ND, `Job 24133 Request for Proposal`, bid item 018,
spec 302 code 0356) **was named by no field description at all**. Measured before: it landed in
`shoulder_tons` 3 times in 10 and in no bucket the other 7 — a silent capture failure, which is
worse than an unstable number because nothing downstream can see that anything was lost. (The
`after_fix1` arm caught it wandering into `base_tons` 3/10 instead, confirming the item is
unanchored rather than mis-assigned.)

**After: `shoulder_tons = 170` on 8 of 8 parseable runs (8 of 10 attempts).**

### The bucket is an ASSUMPTION and is labelled as one, in the prose itself

CSI has **not** ruled on aggregate surfacing. The open questions in
`quantity_crosswalk.py::CSI_OPEN_QUESTIONS_2026_08_07` are riprap and crushing/stockpile — an
earlier claim tonight that aggregate surfacing was among them was a mis-citation and is corrected
here. Basis for the assumption, strongest first:

1. **NDDOT's own distinction.** §302 covers both `Aggregate Base Course Cl__` and `Aggregate Surface
   Course Cl__`; the only difference in the two names is the word Base/Surface, and the class
   numbering is shared (Tier-1 spec-book sweep, `docs/_session/2026-08-10-spec-books-tier1.md`;
   rows 36–37 of `05_knowledge/2026-08-10-spec_item_lookup.csv`, ND pdf p.205). The state calls this
   item a *surface* course, so it is surfacing. That is the state's own distinction and it beats our
   inference.
2. **This file's existing surfacing clause.** `AGGREGATE SURFACING CLASS 1/2/5/SPECIAL` is already
   counted in `shoulder_tons` "pending a CSI ruling". Putting ND surfacing anywhere else would mean
   two different answers to one question inside one file.

The `shoulder_tons` description now says `ASSUMPTION, not a CSI ruling: CSI has not ruled where
aggregate surfacing belongs; it is counted here to match the state's own 'surface course' naming` —
visible in the prompt, in the schema, and to anyone reading the field list.

`base_tons` gained the matching disambiguator (`AGGREGATE BASE COURSE CL __` counts there,
`AGGREGATE SURFACE COURSE CL __` does not), which is why Job 24133's `base_tons` is null 10/10 after
the change instead of catching the 170 T on a third of runs.

### KNOWN DIVERGENCE from the batch path, recorded rather than hidden

`05_knowledge/quantity_crosswalk.py:88` maps `("CL 13", "base")`, so in the **batch** path
`AGGREGATE SURFACE COURSE CL 13` lands in `base_tons` — the contradiction already flagged in the
spec-item lookup CSV. That file is batch-only, is not on the live path, and was out of scope here.
**The two paths disagree on this one item until CSI rules.** Whoever takes the CSI answer must
change both.

### Coverage test — real corpus rows, not fixtures

`pipelines/plan_reader/01_pipeline/test_material_vocabulary_coverage.py` (8 tests).
Every phrase the descriptions tell the model to look for is asserted against
`00_input/_md_cache/*.json` — the converted page markdown of real corpus plans (~100k lines). The
matcher tolerates the converter's `**bold**` / `~~strike~~` / `<br>` noise between words, which a
literal substring search does not.

**RED first, then green.** Before the schema edits: **3 failed, 5 passed** — the three schema-side
assertions failed (no description named `AGGREGATE SURFACE COURSE`, `base_tons` did not distinguish
Base from Surface, `milling_sy` did not name `BITUMINOUS PAVEMENT RECLAMATION`) while the five
corpus-side assertions already passed, which is precisely the signature of a silent capture failure:
the document is there, the vocabulary is not. After: **8 passed**.

The corpus row the CL 13 keyword matches, verbatim from
`00_input/_md_cache/193968928775465b.json`, page 8:

```
|**018**|**302**|**0356**|**AGGREGATE SURFACE COURSE CL 13**|**TON**|**170.**|||||
```

The test asserts both that the phrase matches a real line **and** that the matched line carries the
measured `170` / `TON`, so a match against some unrelated prose sentence cannot pass it.

Tests skip (never silently pass) when `_md_cache` is absent, since it is gitignored.

## Assumptions labelled in this pass (the full list)

1. **`AGGREGATE SURFACE COURSE CL __` → `shoulder_tons`.** Not a CSI ruling. Basis: NDDOT §302's own
   Base/Surface naming, plus this field's existing surfacing clause. Labelled `ASSUMPTION` in the
   shipped prose. Diverges from the batch crosswalk, which sends it to `base_tons`.
2. **`BITUMINOUS PAVEMENT RECLAMATION` is the same pay item as `FULL DEPTH RECLAMATION`.** Basis:
   Stearns 9813645 prints both names against the identical 70,167 SY, one in the bid schedule and
   one in the "Approximate Major Quantities" summary. Data-validated on one document, so it is an
   assumption, not a rule — labelled in the schema comment.
3. **`STABILIZED FULL DEPTH RECLAMATION` and MnDOT item `2215.504` count as FDR.** Basis: MN §2215
   is titled *Reclamation* and sits in the Base Construction division; SFDR appears in the Stearns
   document's own materials-control table. Not separately measured — no corpus plan in the measured
   set carries an SFDR pay item, so this clause is **unfired vocabulary**, added on spec-book
   evidence and honestly untested.
4. **140,430 is the correct Stearns value.** Basis: arithmetic on the printed bid schedule
   (68,167 + 96 + 2,000 + 70,167), independently reproduced by the model's own decomposition in 8 of
   10 runs. Not confirmed against an rtv-csv — Stearns has no machine-readable bid item list.
