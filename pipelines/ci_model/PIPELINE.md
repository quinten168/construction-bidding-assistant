## Stage 1 — Data Cleaning (`data/`)

**Scripts**: `clean_mn_pit_list.py`, `build_project_competitor_panel.py` → `entity_resolution.apply_registry_mapping()`

**What happens**: Merge 2024+2025, reformat dates, parse locations, extract project IDs, and do raw-format cleanup only (ampersand/whitespace normalization). Bidder-name entity resolution is no longer a separate fuzzy-match + manual-review step — it's resolved entirely by `pipelines/ci_model/01_candidates/outputs/competitor_name_registry - name_variants.csv`. Each `raw_bidder_name` maps to a `competitor_unit_id` via the registry's `comp_name` (the registry *is* the identity — no separate ID is assigned).

| Output | Description |
|---|---|
| `data/processed/CSI_data_combined.csv` | 1,661 projects × 67 cols — primary project-level file |
| `data/processed/projects.csv` | Clean project metadata (project_natural_key, bid_date, state, county, project_type, material quantities) |
| `data/processed/bidder_results.csv` | Bidder-level rows (project_natural_key, competitor_unit_id, bid_amount, bid_rank, did_win, raw_bidder_name) |
| `data/processed/MN_pit_list_cleaned.csv` | Cleaned pit list with lat/lon, access_type, Rating |

## Stage 2 — Candidate Generation (`01_candidates/`)

**Scripts**: `build_candidate_panels.py` → `candidate_filter.py` + `build_training_panel.py`

**What happens**: For each project, build one production V3 pool using only information strictly before the auction date. V3 uses a 90-day same-state default, a temporary 12-month warm-up guardrail for auctions in the first 365 observable days, and a targeted fallback score for proven competitors. The 15 older rules are no longer generated by default; they remain available only with `--include-legacy-rules` for backtesting.

**Inputs**: `projects.csv`, `bidder_results.csv`, `pipelines/ci_model/01_candidates/outputs/competitor_name_registry - name_variants.csv`

**Default rule** (used in production): `v3_90d_warmup_targeted_fallback`

V3 includes an active competitor when at least one of these conditions is true:

1. **90d default** — prior same-county history, prior same-state exact-type history, or same-state bid activity in the prior 90 days.
2. **Warm-up fallback** — for auctions with fewer than 365 days of observable dataset history, same-state activity in the prior 12 months. This handles the left-censoring found in the recent-only winner audit; it is not a permanent 12-month rule.
3. **Targeted fallback score ≥ 1.5** — within the state-history candidate universe (plus priority), `3.0 × priority + 2.0 × historical winner in prior 24m + 1.5 × recurring regional competitor + 1.0 × same-state same-family history`. Recurring regional means at least three same-state bids in the prior 24 months. Same-family history alone does not qualify; a win from an unrelated state cannot widen the pool by itself.

There is no active-entity date gate — `entities=None` is passed to every entry path, since no
entity-active-date registry is maintained. Priority membership comes from the competitor name
registry's `Top Competitors Tag` column, resolved to `competitor_unit_id` via `bidder_results.csv`'s
`raw_bidder_name`.

| Output | Description |
|---|---|
| `data/processed/model1/rule_candidate_set.parquet` | Production V3 `(project_natural_key, competitor_unit_id)` rows with entry flags and fallback score; legacy rules appear only when explicitly requested |
| `data/processed/model1/training_audit_panel.parquet` | Candidates + missed actual bidders (for recall auditing); label `did_bid` added here |
| `data/processed/model1/ranking_training_panel.parquet` | Training-only rows (`was_rule_candidate=1`); negatives are non-bidders in the candidate pool |
| `01_candidates/outputs/*.csv` | Audit reports: pool hit rate, recall, and missed-bidder reasons. `pool_hit_rate = captured actual bidders / pool rows`; it is not ranking P@5/P@10. |

**Candidate source flags** (columns in rule_candidate_set):

| Flag | Meaning |
|---|---|
| `source_same_county` | Competitor bid in the same county before |
| `source_same_state_type` | Competitor bid on same project type in the same state |
| `source_recent_90d_same_state` | Competitor bid in-state in the prior 90 days |
| `source_warmup_12m_same_state` | Warm-up-only same-state activity in the prior 12 months |
| `source_historical_winner_24m` | Competitor won at least one project in the prior 24 months |
| `source_recurring_regional_24m` | Competitor bid at least three times in-state in the prior 24 months |
| `source_same_state_family` | Competitor has prior same-state project-family history |
| `source_priority` | Competitor is in the point-in-time priority policy table |
| `fallback_score` | Weighted V3 fallback score; threshold is 1.5 |
| `candidate_source` | Pipe-delimited entry paths: `90d_default`, `warmup_12m`, `hard_priority`, `fallback_score_ge_1_5` |

## Stage 3a — Pit Features (`01_candidates/build_pit_features.py`)

**What happens**: For each `(project_natural_key, competitor_unit_id)` pair, compute geographic pit proximity using haversine distance. Pit access is categorized: open market, competitor-owned, unknown, Knife River pending. Falls back to county centroid if project coordinates are missing.

**Inputs**: `ranking_training_panel.parquet`, `projects.csv`, `MN_pit_list_cleaned.csv`, `bidder_results.csv`

| Output | Description |
|---|---|
| `data/processed/model1/pit_features.parquet` | 28 pit features per `(project_natural_key, competitor_unit_id)` pair |

**Key pit features**:

| Feature | Description |
|---|---|
| `nearest_open_pit_miles` | Distance to nearest publicly accessible pit |
| `open_pits_within_10/25/50mi` | Count of open pits within radius |
| `nearest_owned_or_restricted_pit_miles` | Distance to competitor's own pit |
| `competitor_pit_distance_advantage_vs_open` | `nearest_open − nearest_owned` (positive = advantage) |
| `has_clear_pit_advantage` | 1 if owned pit ≤ 25 mi and ≥ 10 mi closer than nearest open pit |
| `project_location_missing` | 1 if coordinates unavailable (fallback used) |

## Stage 3b — Ranking Features (`02_features/build_ranking_features.py`)

**What happens**: Merge pit features + build point-in-time historical features using only data strictly before the bid date (no leakage). Joins on all prior bids from `bidder_results.csv`.

**Inputs**: `ranking_training_panel.parquet`, `projects.csv`, `bidder_results.csv`, `pit_features.parquet`, `CSI_data_combined.csv` (for bid_year lookup)

| Feature Group | Key Features |
|---|---|
| Prior activity | `prior_bid_count`, `prior_bid_rate`, `days_since_last_bid` |
| Recency windows | `recent_3m/6m/9m/12m/24m_bid_count` |
| Geographic match | `same_state_prior_bid_count`, `same_county_prior_bid_count` |
| Type match | `same_type_prior_bid_count`, `same_family_prior_bid_count`, `paving_match`, `grading_match`, etc. |
| Capacity | `mix_ton_capacity_ratio` (YTD won tonnage ÷ historical annual average) |
| Project size | `log_mix_tons`, `log_grading_yards`, `project_size_proxy` |
| Project flags | `has_paving`, `has_grading`, `has_base`, `is_reconstruction`, etc. |
| Pit features | All 28 columns from Stage 3a |
| Rule score | Heuristic composite: `3×same_county + 2×same_type + 1.5×same_family + 1×recent_12m − recency_penalty` |

| Output | Description |
|---|---|
| `data/processed/model1/ranking_features.parquet` | ~60 features per row; label column `did_bid` |

## Stage 4 — Model Training (`03_training/`)

**What happens**: Temporal split — train before `2025-01-01`, val `2025-01-01`–`2025-05-01`, test after. Four models trained and compared.

**Inputs**: `data/processed/model1/ranking_features.parquet`

| Script | Model | Tuning Method |
|---|---|---|
| `train_logistic_baseline.py` | Logistic Regression | L2 regularization grid |
| `train_decision_tree_baseline.py` | Decision Tree | depth / min_samples grid |
| `train_svm.py` | SVM | C / kernel grid |
| `train_xgboost.py` | XGBoost | RandomizedSearchCV, 50 iter, scored by PR-AUC |

**Label**: `did_bid` (1 = company actually bid on the project, 0 = in candidate pool but did not bid)

| Output | Description |
|---|---|
| `03_training/outputs/ranking_predictions.csv` | All rows with model score columns (`xgb_score`, etc.) |
| `03_training/outputs/xgboost_model.json` | Best hyperparameters + feature importances |
| `03_training/outputs/*_tuning.csv` | Full tuning results for each model |

## Stage 7 — Reporting Agent (`06_reporting/agent/`)

**Entry point**: `orchestrator.py --project-key <PROJECT_NATURAL_KEY>` (e.g.
`MN_STEARNS_CO_MELROSE_2023-08-03`; was `--job-id <JOB_ID>` before 2026-07-28 — job_id is the client's
local CSV row id, renumbered on every regeneration, so it isn't stable across pipeline runs)

**Inputs**: `ranking_predictions.csv`, `logistic_baseline_model.json`, `competitor_name_registry.csv`, `bidder_results.csv`

**4-step sequential pipeline**:

```
Planner → Executor (ReAct loop) → Reflector → Reporter → Export
```

| Step | Script | What it does |
|---|---|---|
| **Planner** | `planner.py` | Selects top-N competitors from scored rows; classifies threat level (high / medium / low) by bid probability |
| **Executor** | `executor.py` | For each competitor: `predict_and_explain` (logistic feature contributions → top reasons to bid / not bid) then `generate_narrative` (Claude LLM writes a 2–3 sentence natural language explanation) |
| **Reflector** | `reflector.py` | Claude LLM quality-checks each narrative for hallucination or vagueness; flags for human review if failed |
| **Reporter** | `reporter.py` | Assembles full markdown report from narratives + optional LLM polishing pass |
| **Export** | `tools/export_report.py` | Saves to `.md` or `.docx` |

| Output | Description |
|---|---|
| `06_reporting/outputs/reports/bid_report_<PROJECT_NATURAL_KEY>.md` | Full competitor intelligence report with ranked list, narratives, and threat levels |

**CLI options**:
```bash
# Standard run (top 10 competitors, markdown output)
python orchestrator.py --project-key MN_STEARNS_CO_MELROSE_2023-08-03

# Top 15 competitors, docx format
python orchestrator.py --project-key MN_STEARNS_CO_MELROSE_2023-08-03 --top-n 15 --format docx

# Skip LLM calls (deterministic output only, no API key needed)
python orchestrator.py --project-key MN_STEARNS_CO_MELROSE_2023-08-03 --skip-llm
```

## Key Constants (`shared/config.py`)

| Constant | Value | Purpose |
|---|---|---|
| `DEFAULT_CANDIDATE_RULE` | `v3_90d_warmup_targeted_fallback` | Active candidate rule for production |
| `V3_RECENT_WINDOW_DAYS` | `90` | Same-state recent-activity window |
| `V3_WARMUP_HISTORY_DAYS` | `365` | Observable-history period where 12m warm-up is allowed |
| `V3_FALLBACK_SCORE_THRESHOLD` | `1.5` | Minimum targeted fallback score |
| `TRAIN_END_DATE` | `2025-01-01` | Train / validation split boundary |
| `VALIDATION_END_DATE` | `2025-05-01` | Validation / test split boundary |
| `TOP_K_VALUES` | `[5, 10, 20]` | K values used in P@K and NDCG@K evaluation |
| `PRIORITY_TIER` | `1` | Tier for hardcoded priority competitors |
| `DISCOVERY_TIER` | `2` | Tier for rule-discovered competitors |
